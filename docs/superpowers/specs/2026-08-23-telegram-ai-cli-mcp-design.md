# telegram-ai-cli-mcp — design

**Дата:** 2026-08-23
**Ревизия:** 2 (после ревью Codex + Antigravity и решений владельца)

## 1. Что это

AI-first CLI и MCP-сервер для управления **пользовательскими** аккаунтами Telegram
через MTProto. Одна кодовая база отдаёт три поверхности: CLI (`tg-ai …`), MCP-сервер
(stdio) и плагин Claude Code.

Описание репозитория опубликовано и связывает нас обещаниями: мульти-аккаунтность,
импорт tdata и готовых сессий, task-shaped тулы, out-of-band подтверждение опасных
действий, allowlist чатов, аудит каждого исходящего, работа и как CLI, и как MCP.

### Чего это НЕ

- Не Bot API-обёртка — здесь пользовательский аккаунт.
- Не средство массовых рассылок и скрейпинга участников.
- Не конвертер форматов сессий: tdata парсит `opentele-ng`.

## 2. Зависимости: не становимся пятой сущностью

| Пакет | Роль |
|---|---|
| `opentele-ng` (PyPI, репо `stufently/opentele`) | **единственная зависимость по tdata** |
| `tdata-session-exporter` (PyPI, репо `session-auth-lib`) | **не используем** — bundle-авторизация под инфраструктуру владельца с обязательным прокси |
| репо `tdata-session-exporter` (отдельный) | мёртвый дубль, архивировать отдельной задачей |
| `telegram-tdata-session-converter` | офлайн-конвертер форматов; не зависимость и не конкурент |

Код аккаунтов **портируется** из `telegram-save-private-photo-video` (`tgsave/accounts/`,
MIT, тот же автор) — но **не копированием**. Ревью показало, что `loader.py` зависит от
`tgsave.models` и `tgsave.secrets`, а `registry.py` — от `tgsave.db.repo.Repo` и SecretBox.
В объём работ входит собственный слой хранения. Что переносится по существу:
`SessionLock`, `SessionPaths`, `sanitize_label`, `harden_path`, `write_private_text`,
`parse_proxy_url`, `resolve_api`, схема логина. Что **чинится при переносе** — §6.8.

## 3. Стек

Проверено 23.08.2026:

| Компонент | Версия | Почему |
|---|---|---|
| Python | **3.14** | свежая поддерживаемая ветка (EOL 2030-10-31) |
| Telethon | **1.44.0** | последняя стабильная |
| opentele-ng | **1.4.0** | tdata |
| mcp (SDK) | **2.0.0** | только публичный API |
| **click** | **>=8.1** | **не Typer** — см. ниже |
| pydantic / pydantic-settings | 2.x / 2.15 | схемы операций и конфиг |
| cryptography | 50.0.0 | секреты at rest |
| cryptg | 0.6.0 | обязателен: AES-IGE на Python блокирует event loop |
| python-socks[asyncio] | 3.0.0 | прокси |
| pytest / pytest-asyncio | 9.1.1 | тесты |

`requires-python = ">=3.12"` — нижняя граница установки, не пин; CI гоняет 3.12–3.14.

**Почему Click, а не Typer.** Typer выводит CLI из статических сигнатур функций
(`inspect.signature` + аннотации). Мы генерируем команды динамически из реестра
операций, и Typer этому сопротивляется. Click — тот же движок уровнем ниже,
`click.Command`/`click.Option` собираются программно.

**Почему не пиним `mcp`.** Боевой userbot владельца пинит `mcp==1.27.2`, потому что лезет
в приватные атрибуты SDK. Здесь используется только публичный API, поэтому берём
верхнюю границу мажора.

## 4. Архитектура

Образец — `zabbix-ai-cli`: *«MCP-тул — тонкий адаптер над теми же операциями, что
выполняет CLI. Второй реализации нет ни у чего.»*

```
telegram_ai_cli_mcp/
  opspec.py        — реестр операций
  ops/             — accounts.py chats.py messages.py contacts.py admin.py
  cli.py           — Click: разворачивает реестр в дерево команд
  mcp_server.py    — stdio MCP: read-тулы + plan-тулы, никакой второй логики
  accounts/        — loader.py login.py registry.py store.py
  safety.py        — профили, capability matrix, allowlist'ы, лимиты
  plans.py         — стор планов, машина состояний
  audit.py         — двухфазный JSON-lines аудит
  redact.py        — PII-редактор
  render.py        — безопасный вывод в терминал
  config.py        — pydantic-settings: YAML + TGAI_ env
  envelope.py      — единый JSON-контракт
  errors.py        — иерархия + стабильные коды
```

### Операция — Pydantic-модель, а не свой `Param`

Собственная мини-система типов стала бы четвёртой в проекте. Источник истины —
строгая Pydantic-модель входа:

```python
Operation(
    name,
    cli_path,
    mcp_tool,
    input_model,  # pydantic.BaseModel — из него JSON Schema для MCP и флаги Click
    output_model,
    effect,  # READ | LOCAL_WRITE | REMOTE_WRITE
    policy,  # какие allowlist'ы и лимиты применяются
    handler,  # для READ
    planner,  # для REMOTE_WRITE
)
```

⚠️ **В MCP SDK 2 low-level сервер только публикует JSON Schema, но не применяет её.**
Адаптер обязан сам вызвать `model_validate()` на входе каждого тула. MCP-аннотации
(`readOnlyHint` и прочие) — подсказки клиенту, а не граница безопасности; полагаться на
них нельзя.

### Startup-инварианты и parity-тесты

Проверяются при импорте реестра и отдельным тестом: имена уникальны;
`handler XOR planner`; любая `REMOTE_WRITE` не имеет read-scope; **в MCP нет тула,
применяющего план**; нормализованная схема и текст ошибок валидации одинаковы у CLI и MCP.

### Контракт ответа

```json
{"ok": true, "data": {}, "warnings": [],
 "meta": {"returned": 40, "total": 812, "truncated": true,
          "truncated_reason": "limit", "account": "work",
          "redacted": true, "untrusted_content": true}}
```

```json
{"ok": false, "error": {"code": "FLOOD_WAIT", "message": "…", "retryable": true,
                        "retry_after": 42, "suggestion": "…"}}
```

`untrusted_content: true` стоит на всём, что пришло из Telegram — это маркер для
клиента, что содержимое контролируется посторонними.

## 5. Поверхность тулов

### Read — 8 тулов, выполняются сразу

| Тул | Отвечает на вопрос |
|---|---|
| `telegram_fleet` | какие аккаунты, кто авторизован, где протухло, кто залочен |
| `telegram_chats` | диалоги / поиск по названию → chat_id |
| `telegram_chat_read` | история чата: `before_id`, поиск, метаданные медиа |
| `telegram_inbox` | что ждёт ответа прямо сейчас по всему флоту |
| `telegram_search` | поиск сообщений |
| `telegram_whois` | резолв @username / id / инвайта → кто это |
| `telegram_chat_members` | участники и админы чата |
| `telegram_media_fetch` | скачать медиа сообщения |

Чтение **никогда** не помечает прочитанным: `send_read_acknowledge` и `mark_read`
запрещены на уровне кода и покрыты тестом.

**`telegram_whois` не вступает.** По инвайт-ссылке зовётся только
`CheckChatInviteRequest`; `ImportChatInviteRequest` — операция записи и идёт планом.

**`telegram_media_fetch` — это `LOCAL_WRITE`, а не read.** Произвольный путь не
принимается вообще: файл кладётся в серверный download-root под сгенерированным именем,
открывается `O_CREAT|O_EXCL|O_NOFOLLOW`, действуют лимит размера, времени и общая квота;
наружу возвращается непрозрачный `artifact_id`. Иначе тул позволял бы затереть конфиг,
базу планов, `~/.bashrc` или сам файл сессии.

### Write — только через план

| Тул | Что делает |
|---|---|
| `telegram_plan_<operation>` | валидирует и сохраняет намерение. Ничего не отправляет |
| `tg-ai plan show <id>` | состояние и точный preview плана; только терминал |
| `tg-ai plan list` | что ждёт решения; только терминал |

**Отдельный plan-тул на операцию, а не generic `plan_create(operation, params)`.**
Нетипизированный `params` не показывает модели схему полей, и она начинает выдумывать
имена аргументов. Операций ~10, бюджет поверхности выдерживаем:
`send_message`, `reply_message`, `edit_message`, `delete_message`, `forward_message`,
`mark_read`, `join_chat`, `leave_chat`, `create_group`, `invite_user`, `promote_admin`,
`set_profile`. Все генерируются из того же реестра.

## 6. Безопасность

### 6.1 Граница подтверждения — названа честно

**Решение владельца:** документированная граница + аудит и лимиты как страховка.

Как работает: план создаётся кем угодно, применяется командой `tg-ai plan apply <id>`.
В MCP тула apply **нет вообще**.

**Чего это НЕ защищает, и это написано в SECURITY.md прямым текстом:**

> Защита рассчитана на MCP-клиента без доступа к shell и файловой системе. Агент,
> у которого есть выполнение команд (Claude Code, Codex и подобные), может вызвать
> `tg-ai plan apply` сам. Для таких сред граница проходит не здесь: доверие к агенту
> предполагается, а страховкой служат аудит каждого действия, персистентные лимиты
> и то, что любой эффект остаётся видимым в логе.

Формулировка *«подтверждение, которое может прислать агент, — это подтверждение,
которое может прислать инъекция»* остаётся верной и объясняет, почему мы не делаем
`confirm: true` внутри вызова тула. Но она не превращает терминал в доверенный канал
там, где терминал у агента тоже есть. Обещать больше, чем есть, — хуже, чем не обещать.

**Профиль `full` удалён.** Остаются два: `readonly` (по умолчанию) и `plan`.
Прямой отправки без плана в v0.1 не существует ни в одной поверхности.

Путь к настоящей границе (отдельный OS-принципал либо TOTP) описан в `docs/threat-model.md`
как возможное развитие; в v0.1 не входит.

### 6.2 Профили

| Профиль | Что можно |
|---|---|
| `readonly` (default) | только read-тулы; любой `plan_*` отказывает |
| `plan` | read + создание планов; применение только `tg-ai plan apply` |

### 6.3 Capability matrix вместо трёх списков

Трёх списков мало: `forward_message` требует проверки И источника, И назначения;
`edit`/`delete` — чата, message_id и авторства; `create_group` вообще не имеет chat_id на
момент планирования; `set_profile` привязан к аккаунту, а не к чату; `invite`/`promote` —
отдельно чат и отдельно целевой пользователь. Поэтому у каждой операции своя политика:

```yaml
safety:
  read:
    chats:   {allow: [], deny: []}       # группы/каналы: пусто = разрешено
    dms:     {allow: [], deny: []}       # ЛИЧКА: пусто = ЗАПРЕЩЕНО
    members: {allow: []}
    media:   {allow: []}
  write:
    send:    {allow: []}                 # пусто = запрещено везде
    admin:   {allow: []}                 # invite / promote
    join:    {allow: []}
    profile: {enabled: false}
  accounts: {allow: []}                  # какие аккаунты вообще доступны
```

**Решение владельца по чтению:** группы и каналы читаются сразу, **личные переписки —
только перечисленные явно**. Пустой список у `dms` означает «ни одной», а не «все».
Все write-списки fail-closed: пусто = запрещено.

**Жёсткий denylist в ядре, не в конфиге и без опции отключения:**

- чат `777000` (Telegram Service Notifications) — туда приходят коды входа и сброса 2FA.
  Инъекция, попросившая агента «посмотри последний код», получила бы доступ к аккаунту;
- Saved Messages (`me`) — типовое место хранения паролей и документов;
- любой чат, помеченный в конфиге `deny`, перебивает `allow`.

**Все проверки повторяются при `apply`, а не только при создании плана.** Username и
инвайт резолвятся в числовой peer при планировании, снимок сохраняется в плане, и при
применении сверяется заново — иначе между планом и отправкой цель может подмениться.

### 6.4 Лимиты — персистентные, не «за сессию»

Скользящие окна в SQLite: на аккаунт, на цель и на весь флот. Перезапуск процесса
**не обнуляет** лимит — иначе ограничение снимается рестартом. Слот резервируется под
локом ДО сетевого вызова и возвращается только при доказанном отсутствии эффекта, по
whitelist'у **классов** исключений Telethon, а не по тексту сообщения.

Автоматические ретраи и `flood_sleep_threshold` Telethon по умолчанию включены и
способны сами повторить отправку — отключаем явно и управляем ретраями сами.

### 6.5 Машина состояний плана

`pending → applying → applied | failed | unknown_outcome`, плюс `rejected` и `expired`.

- переход `pending → applying` — атомарный conditional UPDATE в SQLite; двух одновременных
  применений одного плана не бывает;
- `plan_id` — 128 бит из CSPRNG, не последовательный;
- у планов есть TTL, команда `tg-ai plan reject <id>` и квота на число pending;
- тело сообщения в базе планов хранится зашифрованным;
- **`unknown_outcome`** — таймаут после отправки RPC. Это не «не отправилось»:
  автоматический повтор здесь удваивает сообщение. Такой план требует ручного разбора.

### 6.6 Аудит — двухфазный

`attempt` пишется ДО RPC, `outcome` — после, обе строки с одним `plan_id`. Односторонняя
запись «после успеха» теряет ровно тот случай, ради которого аудит и нужен. Запись —
JSON-lines с межпроцессным локом и `fsync`; control-символы экранируются на входе, чтобы
лог нельзя было подделать escape-последовательностями. Тело сообщения — хеш и длина;
`--audit-full` включает тело осознанно.

### 6.7 Безопасный вывод в терминал

Всё, что пришло из Telegram, проходит через `render.py` перед показом: ANSI escape,
OSC-последовательности, `\r`, control-символы и bidi-override вырезаются.
Иначе текст сообщения способен перерисовать `tg-ai plan show` так, что человек
подтвердит не то, что видит, — а на этом просмотре держится вся конструкция аппрува.
`--raw` существует только в CLI и **отсутствует в MCP**.

### 6.8 PII-редактор

Включён по умолчанию. Кроме телефонов, email и номеров карт обязательно ловит
специфичное для Telegram: seed-фразы (12/24 слова), адреса TON (`EQ…`/`UQ…`) и EVM
(`0x…`), одноразовые коды и токены. Оговорка в документации: редактор не делает
переписку неперсональной — имена, username и сами тексты остаются, поэтому основная
защита от утечки это allowlist чтения, а не редактор.

### 6.9 Хранение — что чиним при портировании

Переносится: `0700`/`0600`, атомарная запись `O_CREAT|O_EXCL` + fsync + `os.replace`,
flock на файл с auth key, замороженный device fingerprint, 2FA только через `getpass`.

Чинится (ревью нашло в исходнике):

- **`api_hash` лежал открытым** в `<label>.api.json` вопреки обещанию AES-GCM — шифруем;
- **ошибка `chmod` только логировалась** — это fail-open; теперь отказ;
- **«симлинки не следуются»** верно только для hardening: последующее чтение профиля,
  сессии и tdata шло по ссылке — открываем с `O_NOFOLLOW`;
- **lock строился по строковому пути** — алиасы одного auth key получали разные локи;
  ключ лока считаем по `st_dev`+`st_ino`;
- сам `.session` содержит **открытый 256-байтный auth key**: `0600` спасает от соседей,
  но не от бэкапа. Документируем требование шифровать раздел/каталог;
- `AuthKeyDuplicatedError` и `SessionRevokedError` переводят аккаунт в статус `revoked`
  без бесконечного реконнекта;
- `fcntl` делает реализацию **POSIX-only** — заявлено явно, Windows не поддерживается в v0.1.

### 6.10 Никаких наших данных

В репозиторий не попадает ничего из инфраструктуры владельца: номера, имена аккаунтов,
chat_id рабочих чатов, домены внутренних сервисов, хосты прокси, имена боевых сессий.
Тест `test_no_private_data.py` проверяет структурные признаки (E.164, отрицательные
chat_id, IP); полный список запрещённых строк лежит **вне репозитория**, путь из
`TGAI_PRIVATE_DENYLIST`. Перечислять сами значения в публичном репо нельзя — это ровно
та утечка, которую тест предотвращает.

## 7. SEO и GEO — репозиторий должен находиться

Задача владельца: выжать максимум находимости, и людьми через поиск, и ИИ-ответчиками.
GEO (generative engine optimization) здесь важнее классического SEO: инструмент ищут
запросом «MCP server for Telegram», и ответ даёт LLM, а не выдача.

- **Topics GitHub** (сейчас пусто): `mcp`, `mcp-server`, `model-context-protocol`,
  `claude-code`, `claude`, `cli`, `ai-agents`, `ai-tools`, `llm-tools`, `telegram`,
  `mtproto`, `telethon`, `userbot`, `python`, `automation`. Держим 15–20, как в
  `zabbix-ai-cli` и `yandex-mcp`.
- **README как цитируемый источник.** Первый абзац отвечает на вопрос целиком, без
  отсылок («telegram-ai-cli-mcp is a CLI and MCP server that …») — LLM цитирует
  самодостаточные пассажи. Дальше: раздел вопрос-ответ с формулировками реальных
  запросов, таблицы (их модели извлекают точнее прозы), явные версии и даты.
- **`llms.txt`** в корне — краткая карта проекта для ИИ-читателей.
- **Метаданные пакета:** `keywords`, `description`, `Project-URLs` в `pyproject.toml`
  дублируют те же термины — PyPI индексируется и поиском, и ассистентами.
- **Social preview** и заполненный About в репозитории.
- **CITATION.cff** — даёт каноническое имя и авторство, которое ассистенты подхватывают.
- **Перелинковка с соседями** (`zabbix-ai-cli`, `yandex-mcp`): линейка продуктов одного
  автора усиливает друг друга.
- Публикация в PyPI и MCP registry — сильнейший сигнал находимости, но она **отложена**
  до отдельного решения владельца (§12).

## 11. Порядок работ

Исправлен по обоим ревью: safety идёт ДО read-операций, иначе их пришлось бы переписывать.

1. Скелет репо, **исправленный `.gitignore`**, CI, `errors.py`, `envelope.py`.
2. `config.py` + автономный `accounts/` со своим хранилищем.
3. **Safety kernel:** `safety.py`, `plans.py`, `audit.py`, `redact.py`, `render.py`.
4. `opspec.py` — вертикальный срез: одна операция проходит Pydantic → CLI → MCP → schema,
   с contract-тестами.
5. Read-операции целиком + CLI чтения.
6. Первый write end-to-end (`send_message`) с тестами на гонку и `unknown_outcome`.
7. Остальные write-операции.
8. MCP-сервер, smoke-тест.
9. Плагин, скилы, документация, SEO/GEO-обвязка.

⚠️ **Шаги 1–4 делаются основным потоком, а не раздаются субагентам.** Общий `Operation`,
машина состояний плана и capability matrix — зоны максимального расхождения; параллелить
их до фиксации контрактов значит получить три несовместимые реализации. Субагенты
подключаются с шага 5, когда контракты уже заморожены.
